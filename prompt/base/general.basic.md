# 开发指南

本文件是所有项目共用的基线规范，只写模型不会自带、或与默认行为相反的约定。
具体到某个项目的技术栈、命令和风格，写在该项目根目录的 `AGENTS.md` 里。

## 语言约定

- **对话**：使用中文与用户沟通、解释与汇报。
- **代码与注释**：跟随项目既有语言，不要在同一个仓库里混用两种语言。
  拿不准就先看相邻文件写的是什么。
- **提交信息与 PR**：同上，跟随项目既有语言。项目 `AGENTS.md` 有明确规定时以它为准。

## 任务状态：`IMPLEMENTATION_PLAN.md`

复杂任务的进度记录在项目根的 `IMPLEMENTATION_PLAN.md`，任务完成后删除。

**开工前必须先用直接路径 `read_file` 检查这个文件是否存在。**
它通常被列在 `.gitignore` 里，不会出现在目录列表和搜索结果中——用 `grep`、`glob`
或列目录都看不到它，必须显式设置 `no_ignore=true`（或等效参数）。看不到不等于不存在，
漏读就会把做了一半的任务从头再做一遍。

存在就从当前阶段继续，不存在才开始新的规划。

阶段格式（`skills/base/architect-planning` 有完整说明和校验脚本）：

```markdown
## 阶段 N: [名称]
**目标**: [交付什么]
**成功标准**: [可测试的结果]
**状态**: [未开始|进行中|已完成]
```

## 卡住时：同一问题最多试 3 次

第 3 次失败后停下，不要继续变着花样重试。改为：

1. 记下每次试了什么、报什么错、根因判断是什么
2. 在代码库里找 2-3 个类似实现，看它们怎么做
3. 质疑假设——抽象层级对吗？问题能不能换个问法？是不是该**移除**抽象而不是再加一层？
4. 把结论告诉用户，需要决策就问

## 提交

- 在特性分支工作，不直接提交主分支
- 提交粒度小而专注，遵循 Conventional Commits
- **绝不**在共享分支上 `--force` / `--force-with-lease`
- 交付前跑项目自己的格式化、Lint 和测试命令（具体命令见项目 `AGENTS.md`）

## 底线

- 不禁用测试来让它变绿，要修就修真的原因
- 不提交跑不起来的代码
- 不凭记忆猜 API 和文件内容——去代码库里读
