# 开发指南

## 交互标准 (关键：语言规则)

**⚠️ 强制规则：核心技术用英文，文档与沟通用中文**

1. **对话语言**：始终使用 **中文** 与用户沟通、解释逻辑并提供反馈。
2. **技术产出**：所有代码、代码注释和 Commit Message 必须使用 **英文**。
3. **任务规划与文档**：详细的实施计划（`IMPLEMENTATION_PLAN.md`）以及 Pull Request 的标题和描述必须使用 **中文** 编写。
4. **任务边界**：`TaskName`（任务名）、`TaskStatus`（任务状态）和 `TaskSummary`（任务总结）应使用 **中文**，以便用户理解。
5. **专业性**：确保在中文解释中正确使用英文技术术语。

## 开发哲学

### 核心原则

- **增量迭代优于大步跳跃** - 小步快走，确保每次更改都能编译并通过测试。
- **向既有代码学习** - 在编写代码前，先研究项目中已有的实现模式。
- **实用主义优于教条主义** - 适应项目现实，避免过度设计。
- **意图清晰优于奇技淫巧** - 选择直接、简单的解决方案。

### 解决问题的思维

- 修改代码时，专注于当前问题。除非必要，否则避免修改已验证的逻辑。

### 所谓简单

- 每个函数/类只有单一职责。
- 避免过早抽象。
- 选择能完成工作的最简方案。
- 如果需要过多解释，那说明它太复杂了。

## 洁净代码原则

### 魔术字

- 用文件顶部或专用常量文件中的具名常量替换重复或含义不明的数字。
- 如果魔术字能提高测试的可读性，则在测试中是可以接受的。

### 有意义的命名

- 变量、函数和类应能揭示其用途。
- 命名应解释其存在的原因以及如何使用。
- 除非是通用的缩写，否则避免使用缩写。

### 智能注释

- 不要注释代码在“做什么”——让代码本身具有自解释性。
- 解释“为什么”选择某种特定的实现。
- 记录 API、复杂算法和非显而易见的副作用。

### 单一职责

- 每个函数应只做一件事并做好。
- 函数应保持短小且专注。

### DRY (不要重复自己)

- 将重复的代码提取到可重用的函数中。
- 通过适当的抽象共享通用逻辑。

### 结构清晰

- 将相关的代码放在一起。
- 按逻辑层级组织代码。
- 对文件和文件夹使用一致的命名约定。

### 封装

- 隐藏实现细节。
- 暴露清晰的接口。
- 将嵌套的条件语句移至命名良好的函数中。

### 持续改进

- 持续重构。
- 尽早处理技术债。
- 保持离开时的代码比发现时更干净。

### 重构准则

- 重构期间保持测试逻辑不变。
- 确保每一步重构后所有测试都能通过。

## 开发流程

### 0. 状态恢复 (关键)

在开始任何任务或探索之前：
- **强制操作**：直接使用 `read_file` 检查根目录下是否存在 `IMPLEMENTATION_PLAN.md`。
- **原因**：此文件可能被 `.gitignore` 忽略，不会出现在目录列表或标准搜索中。
- **结果**：如果发现该文件，从当前阶段恢复任务。如果未发现，才开始初始规划。

### 1. 规划与分阶段

在 `IMPLEMENTATION_PLAN.md` 中将复杂工作分解为 3-5 个阶段：

```markdown
## 阶段 N: [名称]
**目标**: [详细描述交付内容]
**验收标准**: [可测试的结果]
**测试用例**: [具体的测试用例]
**状态**: [未开始|进行中|已完成]
```

标准结尾阶段：

```markdown
## 代码简化阶段
**目标**: 确保使用了最简单的方案。
**验收标准**: 实现方式直接且易读。
**状态**: [未开始|进行中|已完成]

## 规范审查阶段
**目标**: 确保符合开发和风格指南。
**验收标准**: 所有代码均符合项目标准。
**状态**: [未开始|进行中|已完成]

## 验证与清理阶段
**目标**: 检查最终实现中的错误并清理项目环境。
**步骤**:
- 运行静态分析工具。
- 验证命名一致性。
- 删除多余的空格。
- **关键操作**：删除 `IMPLEMENTATION_PLAN.md` 以及为该任务创建的所有其他临时文件。

**验收标准**: 所有验证步骤已完成且工作区整洁。
**状态**: [未开始|进行中|已完成]
```

- 随着进度更新状态。
- 所有阶段完成后删除该文件。

**⚠️ 处理 Gitignore 文件**：
请注意 `IMPLEMENTATION_PLAN.md` 或其他核心流程文件可能被列在 `.gitignore` 中。
- 如果预期文件存在，始终使用直接路径调用 `read_file`。
- 如果使用 `grep_search`、`glob` 或 `list_directory`，请显式设置 `no_ignore=true`（或等效参数）以查看这些文件。
- 绝不要因为文件未在默认列表显示就认为它不存在。

### 2. TDD 实现

1. **理解** - 研究现有模式。
2. **测试** - 编写一个失败的测试 (Red)。
3. **实现** - 编写通过测试的最少代码 (Green)。
4. **重构** - 在保持测试通过的同时优化代码。
5. **提交** - 编写清晰的英文 Commit Message。

### 3. 处理困难 (最多尝试 3 次)

**核心原则**：对同一个问题尝试 3 次失败后，停止并重新思考。

1. **记录失败的尝试**：
   - 尝试的方法。
   - 具体的错误信息。
   - 根因分析。
2. **研究替代方案**：
   - 寻找 2-3 个类似的实现。
   - 记录不同的方法。
3. **质疑假设**：
   - 抽象层级是否正确？
   - 问题能否被简化？
4. **从不同角度尝试**：
   - 使用不同的库特性？
   - 更改架构模式？
   - 移除抽象而不是增加抽象？

## 技术标准

### 架构原则

- **组合优于继承** - 使用依赖注入。
- **接口优于单例** - 便于测试和灵活性。
- **显式优于隐式** - 保持清晰的数据流和依赖关系。
- **测试驱动** - 修复测试而不是禁用它们。

### 代码质量

- **每次提交必须**：
  - 成功编译/构建。
  - 通过所有现有测试。
  - 包含新功能的测试。
  - 符合格式化和 Lint 规则。

- **提交前**：
  - 运行格式化工具和 Linter。
  - 自我审查更改。
  - 在 Commit Message 中解释“为什么”。

### 错误处理

- 快速失败并提供详细的错误信息。
- 提供调试上下文。
- 在适当的层级处理错误。
- 绝不要静默吞掉异常。

## 决策框架

当有多种方案可行时，优先级排序如下：

1. **可测试性** - 是否容易测试？
2. **可读性** - 6个月后是否依然清晰？
3. **一致性** - 是否遵循现有模式？
4. **简单性** - 是否是最简可行的方案？
5. **可逆性** - 以后修改有多难？

## 项目集成

### 学习代码库

- 寻找 3 个类似的功能/组件。
- 识别通用的模式和约定。
- 尽可能使用相同的库/工具。

### 工具使用

- 使用项目现有的构建系统、测试框架和 Lint 配置。
- 除非有充分理由，否则不要引入新工具。

### 完成的定义 (Definition of Done)

- [ ] 测试已编写并通过。
- [ ] 代码符合项目约定。
- [ ] 无 Lint/格式化警告。
- [ ] 无未使用的导入。
- [ ] Commit Message 清晰（英文）。
- [ ] 实现与计划一致。
- [ ] 无未关联 Issue 的 TODO。

## 实现细节

### 函数

- 在可能影响清晰度的情况下避免使用默认参数。
- 保持参数数量较低（理想情况下 < 3个）。

### 包管理

- 识别并使用项目现有的包管理器（npm, yarn, poetry 等）。

## 版本控制

### 审查更改

- 使用 `git --no-pager diff HEAD` 审查当前的更改。

## GitHub 标准

### 提交 (Commits)

- 如果适用，遵循 Conventional Commits。
- 提交信息（Commit Message）使用 **英文**。
- 在特性分支工作；避免直接提交到主分支。
- 进行短小且专注的提交。
- 绝不要在共享分支上使用 `--force` 或 `--force-with-lease`。

### Pull Requests

- PR 标题和描述使用 **中文**。
- 提交前运行 `pre-commit` 钩子。
- 使用 `gh pr list` 检查现有的 PR。

## 最后提醒

**绝不**：
- 禁用测试而不是修复它们。
- 提交无法构建的代码。
- 凭空猜测——请通过代码库进行验证。

**始终**：
- 提交可工作的代码。
- 保持实施计划持续更新。
- 向现有实现学习。
- 失败 3 次后重新评估。
