01执行摘要

一句话：CodeAgent 的实际健康度，比从外面看它的结构要好得多。

这不是一个正在腐烂的项目——它是一个年轻的、在被积极重构的项目，而且同规模项目里少有地自律：core/ 和 engines/ 里 TODO/FIXME 为零，覆盖率有带说明注释的棘轮门槛，lint 规则的启用/禁用都写明了理由，提交信息记录的是"为什么"（大量 fix 提交读起来就是一轮轮自审的后续）。真正的风险不是腐烂，而是三个正在叠加效应的结构性决策：

① 一套 4,526 行的 Agent Gateway 双栈悬空：主 UI 已经退役提交 4440181「退役 Web Agent」删掉了 Web Agent 页签，但 gateway 仍在启动路径上运行、仍持久化到 SQLite（schema v4）、仍暴露 6 个端点。
② 核心卖点"加一个引擎"的实测成本：约 37 个文件Antigravity 提交（c7adcdf）改了 48 个文件（+2,563 行），其中真正的新适配器代码只有约 1,143 行，其余是放射到约 20 个既有模块的连带修改。
③ 危险默认值，出现两次交互式 Codex 默认带 --dangerously-bypass-approvals-and-sandbox 启动；回环 Web API 默认无 token——两者各自都有文档论证，但组合起来就是"模型无沙箱地改文件 + 本机任意进程能开 shell"。

04架构问题

模块边界、依赖方向，以及那个关键的扩展点问题。

AUDIT-001 · Agent Gateway 双栈悬空 P1 高置信

core/services/agent_gateway/*（898 行）· agent_adapters/*（2,358 行）· agent_store.py · agent_protocol.py · core/web/routers/agent.py（368 行）· chat.py · instances.py · e2e.py · server.py lifespan
证据
提交 4440181「refactor(ui): 退役 Web Agent,终端成为唯一的对话入口」删除了 AgentWorkspace.tsx。navigation.ts 注释明确说明基于 gateway 事件的聊天页"已被退役"。但 server.py:237-248 仍在 lifespan 中构建 adapters + AgentGateway + AgentStore 并启动。剩余消费者只有：agent.py（REST/WS）、instances.py:43（只读状态）、chat.py:43（只读 legacy_fallback 开关）、e2e.py。
问题
两套 adapter 体系并存：engines/start_*.py（启动注入型）与 agent_adapters/*（SDK/JSON-RPC 程序化型）。后者的主 UI 已经没了。
根因
gateway 是正确的长期方向（行业也在验证这个方向，见第十二章），但产品迭代发现终端流式体验更好，先砍了 UI，代码留了下来。
影响
约 4.5k 行代码 + sqlite 迁移（v4）+ 6 个端点 + FakeAgentAdapter 环境变量的持续维护税；新人必须同时理解两套 session 概念。
建议方向
二选一并显式化：(a) 保留为实验特性——默认 CA_AGENT_GATEWAY_ENABLED=0 + README 标注 experimental；(b) 若短期无回归计划，归档到独立分支。倾向 (a)：claude-agent-sdk 那个适配器写得很好，且行业趋势支持。
范围 / 风险
Small / Low · 值得现在修：是

AUDIT-002 · 新增引擎的成本——核心架构指标 P1 高置信

实测自提交 c7adcdf「全面接入 Google Antigravity (agy) 引擎」：48 个文件，+2,563 −104 · 非测试文件 37 个
证据
真正的新代码约 1,143 行：start_antigravity.py（93）+ collector（341）+ parser（576）+ writer（133）。放射到约 20 处的连带修改：constants、cli/main、cli_utils、doctor、i18n、runner_service、resume_commands、mcp_service、session 的 models/finder/parsers/writers 注册、analytics 的 service/models、web 的 4 个 router、cli 的 4 个命令、前端 4 个文件。
根因
没有 Engine Registry。"引擎"的知识散落在：constants.ENGINES（frozenset）· cli/main.py:50-57 的 engine_script_map（硬编码路径映射）· runner_service._build_engine（if 链式懒加载）· _CHAT_SESSION_ID_FIELDS · cli/commands/tasks.py batch-run 的 click.Choice · doctor.py 的 ENGINE_BINARIES + INSTALL_HINTS · mcp_service.py 的各引擎配置路径 · 前端 ENGINE_LABELS。
影响
每加一个引擎都要"记得"改约 20 处，漏掉任何一处都没有告警。doctor.py 自己的注释就承认了："an engine missing here is one the health check silently says nothing about"（引擎不在这里 = 健康检查对它沉默）。这正是产品头号卖点（LLM 无关性）的扩展瓶颈。
建议方向
做一个声明式 EngineSpec（name、aliases、binary、install_hint、script、headless、mcp_paths、session_id_fields、display_name）。CLI 映射、doctor、Choice、前端（经已有的 /api/engines）全部从它派生。预期效果：新引擎触点从 ~20 降到 ~8（5 个新文件 + 3 个注册点）。
范围 / 风险
Medium / Low-Medium（纯收敛，行为不变）· 值得现在修：是——最高优先级

其他边界结论

  • 无循环依赖。runner_service._build_engine 在函数内懒 import 引擎模块，明确绕开 core→engines→core 环——有注释说明，属可接受取舍。
  • Web↔Core 耦合适度。router 调 service 层，没有 router 直接伸手进扫描器内部。唯一皱点：routers/tasks.py 与 routers/chat.py 通过裸导入共享单例 _runner（# noqa: F401 — shared singleton）——能用，但属隐式耦合。
  • 没有 God Module。cli/main.py 只有 141 行；server.py 组装职责清晰。
  • AUDIT-008 值得在做完整 registry 之前单独立项：CLI 的 map、click.Choice、_build_engine 都应从 constants.ENGINES 派生——这个常量已经存在，却被它自己的消费者绕过了。

05代码结构问题

core/ 26,234 行 + engines/ 1,853 行 + 前端 ~15,344 行 + 测试 20,708 行。

AUDIT-005 · start_codex.py（934 行）—— 八问八答拆解

为什么这么大？
约 40% 是 CodexEngine 类（与 opencode/claude 对等），约 60% 是模块级机器：code-plan 模式（历史载入/保存、交互选择、range）、shell:first 块提取器与预启动命令执行器、marketplace/cache 插件注册。
内聚吗？
不。三个可以独立测试的子系统，被"因为 codex 需要它们"堆进了 adapter 文件。
该拆什么？
shell_first.py（run_prelaunch_commands 有确认门 / 环境变量门 / fail-closed 设计，值得独立测试）；code_plan.py；marketplace 注册可并入插件机制。
拆分边界？
类留在原文件；三个模块级子系统各成一个文件；main() 负责编排。
拆后依赖更复杂吗？
更简单——shell:first 和 code-plan 互相依赖，但都不依赖引擎类。
值得拆吗？
值得，且风险低：34% 的覆盖率正是"先拆再补测试"的动机。
怎么渐进式拆？
先搬 extract_shell_first_blocks + run_prelaunch_commands（已有 415 行的 test_codex_shell_first.py 直接保护），再搬 code-plan。

其他结构发现

  • P2 AUDIT-013——pty.py（1,046 行）：tmux 会话管理、POSIX/ConPTY 双路 PTY 泵、WS 消息循环、_ACTIVE_SESSIONS 注册表、resize 处理。内聚度中等；拆分边界清晰（tmux 层 / 会话注册表 / 路由），但不紧迫——测试覆盖 90%。
  • P3 AUDIT-019——hook_service(57) / skill_service(92) / prompt_service(72) / plugin_service(50) 是 Scanner 的薄包装，多半只为 Web 端点存在。无害，但"Service"一词通胀，模糊了它们与真 service（runner/scheduler/config）的区别。
  • P3 AUDIT-017——三个内容完全相同的 frozenset（ENGINES/HEADLESS_ENGINES/MCP_ENGINES）。注释暗示曾经不同；现在要么派生要么删。
  • 没有死代码、没有注释掉的旧代码、没有魔法数通胀。常量集中在模块顶部并带解释（如 RUN_RETENTION_DAYS=30 / KEEP=200）。_LEGACY_PROBE_NAMES 这类历史清扫代码有明确的生命周期注释。
  • 重复代码判定：每个引擎的五连 finally: 清理是可接受的（顺序与目标路径确有差异）；五个 analytics collector 各自独立是正确的——各家 JSONL/schema 差异真实存在，强行抽公共基类只会增加间接性而不减少复杂度。

06CLI / Engine 编排——核心能力评估

CLI —— 8/10

CodeAgentGroup.resolve_command 把"保留子命令"与"第一个参数是引擎名"两种派发分开，再加 _launch 兜底——这是一个务实的设计，让 ca claude do something 和 ca "do something" 两种心智模型共存。Epilog 带示例；-y 默认开且打印警告；i18n 覆盖到 help 文案与错误提示。缺：shell 自动补全（click 原生支持，便宜可捡）和 ca ps --json（可脚本性）。

Engine 启动架构 —— 7/10

这是项目最真实的价值所在，细节质量很高：

  • OpenCode 没有 settings.json 概念 → 生成 JS 桥接插件来跑 shell 钩子，带工具名归一化表（TOOL_NAME_MAP：bash→Bash…），denial 语义经 throw 转换——四个引擎共享同一份钩子契约，注释证明是实测结论（"opencode 1.18 的二进制里完全搜不到该文件名"）。
  • 所有注入文件都带标记 _ca_injected: true，拒绝覆写非托管路径，崩溃残留由 doctor 清扫（包括对 .codex/config.toml 的 TOML 解析，以及 with_name(name+".bak") 备份路径 bug 的修复史）。
  • write_temp_prompt 用系统临时目录 mkstemp 解决命令行超长问题；resource lock 防并发注入。
  • Windows 投入是真实的：junction 探测放进私有临时目录、\\?\ 长路径、taskkill /T、ConPTY、PowerShell shell:first。

减分项：AUDIT-003/004（见第九/十一章）与 AUDIT-012——codex 插件挂载需要改写用户全局的 ~/.codex/config.toml（marketplace 注册 + cache install + enabled 状态）。虽有保留式备份还原和两轮崩溃保护注释，但崩溃窗口加上 "MARKETPLACE_NAME not in content" 这种启发式判断，意味着脏写仍可能发生。如果 Codex 原生 marketplace 格式变化，这里会是第一个断裂点。

07Prompt / Skill / Plugin / Hook / Task——资源体系

五个概念——是真实边界还是概念通胀？判定：真实边界。

概念生命周期载体判定
Prompt注入合成后的 prompt 文本markdown + scanner必要
Skill符号链接挂载 SKILL.md + scripts目录 + scanner + links必要
Hookbefore/after_tool 外壳命令，按引擎注入metadata.json + settings/bridge必要（对齐 Claude Code 语义）
Plugin把以上三者打包分发_plugin_dir + 生成适配器必要（分发单元）
Task可重放的执行蓝图tasks/*.md + task_lib必要（自动化单元）

Group（资源组）+ Scanner + Mount + project_registry 的绑定模型是连贯的；ca resources list --group 能核对生效状态；doctor 会检查解析失败。唯一的重叠：AUDIT-014——codex 的 -cp code_plan 模式重新实现了一遍 task 机制（同样的选择/历史/range 流程，差别只有后缀 .md、code_plan* 目录和独立的 history.json）。应该回灌进 core/task_lib。

性能：扫描器每次启动重跑（目录小，毫秒级）。没有扫描缓存，而且不需要加——别为此加缓存（防过度设计）。

08Session / Scheduler / Background / Analytics

Session 子域 —— 好

parsers(5) + writers(5) + session_finder + parse_cache + audit 已经构成独立子域，模型统一，每个引擎都有 convert-contract 测试。OpenCode 解析器直读 sqlite，parse_cache 用行数 + 最新行时间做变更令牌（注释里量化过：~20ms vs 1.3s 全量重解码）——质量很高。唯一瑕疵：AUDIT-016 的连接泄漏。

Scheduler —— 好

scheduler_tick_loop（30 秒 tick）、_settle_finished_runs 把 "started" 结算成真实终态（修掉了"任务 30 秒前就失败了，状态还挂着 started"）、workspace 三类校验错误分别记账、prevent_overlap、webhook 尽力而为不阻塞事件循环。教科书级的小型调度器。

三套执行抽象 —— AUDIT-011

run_task（子进程跑 ca <engine> -t）、run_chat_turn（直接调 build_chat_command，绕过注入——v1 范围有文档说明）、AgentGateway session（SDK/长连接）。三者有真实差异（是否注入、是否长连、谁管生命周期），不算重复系统。但在概念上，用户看到的是 Tasks/Chat/Terminal 三个互不引用的东西。尤其是 run_chat_turn 跳过资源注入这个事实，应该在 UI 上可见（用户会疑惑为什么 chat 回答没带 skills）。

Analytics —— 好，但有软肋

collector 水位增量 + BACKFILL_VERSION 回填协议（v5）正确处理了"新可见的旧记录"；codex 全量重扫有明确理由（session 级可变 token 总量）；disk cache + 双重检查锁 + 预热线程。软肋 = AUDIT-009：手工维护的定价表加上 _UNKNOWN 落回 Sonnet 价格，意味着新模型上线就会静默报错误成本，而且 UI 不区分"精确/估算"。建议：数据外置 JSON + 加载时新鲜度戳 + UI 估算标记。

09Web UI / UX

UI —— 7/10

信息架构是刻意修剪过的五个区（Home / Agent / Automations / Activity / Settings），而且删除决策都带理由（Timeline 被删是因为"它搜索的是客户端封顶窗口，回答不了它想回答的问题"）。shared/ 有 20 个小部件（EmptyState / ErrorState / Toast / ConfirmDialog…），错误与空态是系统化的，不是每页自造。React Query + 轮询 hook + 异步守卫 hook 是正规军打法。深色模式和信息密度良好。大组件（AUDIT-018）可以接受，但 ConfigHub 已到"每加一个配置项都变难"的临界点。

UX —— 7/10

优秀的地方：ca doctor --fix（config 种子、stale 注入修复带 --dry-run 预览、codex trust 警告、MCP 漂移检测）；首次启动的 group 绑定引导；ca switch 一步转换+直接拉起；错误信息直接给出下一步命令（"Run: ca doctor --fix"）。

最大的 UX 风险（AUDIT-003/004）：build_command() 在交互模式下也带 --dangerously-bypass-approvals-and-sandbox；-y 默认 True 只配一行警告。对比 codex CLI 自己的审批体系，这等于把引擎原生安全层整体短路，而且新用户未必理解那行警告。security.py auth_enabled()：回环默认免 token（docstring 论证充分：Host+Origin 已挡住浏览器攻击，同用户进程本来就能读 token 文件）。但残余风险是真实的：本机任意低权限进程可以 POST /api/pty 拿到一个 shell。建议方向——不动架构：(a) codex 交互默认走审批，仅在显式传 --yolo 时 bypass（其他引擎维持现状）；(b) 提供 CA_UI_AUTH=1 的一键文档路径；回环默认可以保留——非回环警告文案已经存在，这点做得好。

10测试与质量

受保护的核心（1,059 个测试 / 84 个文件 / 78.15% / 棘轮 76 / 单测 60 秒超时 / Playwright e2e + axe-core 无障碍 / 前端 vitest 40 个文件）：agent_gateway（659 行测试）、PTY（1,069）、ca_launcher（1,057）、session_history（1,050）、每个引擎的 convert contract、scheduler_loop、auth（含 bind-address 跟随）、Windows 长路径原子写。隔离用 fixtures/fake_pty_engine；没有 sleep 依赖的坏味道；套件 57–63 秒稳定。

保护最薄弱的，按风险排序：

  1. P2 AUDIT-006——engines/start_codex.py 34%、start_opencode.py 39%——恰好是含 shell:first 安全门、marketplace 改写、崩溃恢复逻辑的两个文件。test_codex_shell_first.py 护住了预启动命令，但 ensure_plugins_available 的备份/还原矩阵和 cleanup_plugins_available 的各分支（备份存在 / 不存在 / config 已脏）没有直接测试。
  2. doctor 的 fix 路径（fix_stale_injections）测过，但 _sweep_legacy_probes 的 Windows junction 分支只能在 Windows CI 上真正执行——而它不存在。
  3. 没有 Windows CI job——代码里有大量 win32 分支；建议加一个 windows-latest job（可先设为允许失败）。

12.3 CodeAgent 反而做得更好的

  1. 会话跨引擎带走（ca switch）——矩阵中独一无二。新出现的编排项目证明这个需求存在，但没有一家做到了格式级 parser + writer + contract 测试。
  2. MCP 配置同步 + 漂移检测——各家原生 MCP 配置互不相通，CodeAgent 是唯一直读各家原生格式（甚至处理 JSONC 注释）并做 sync 的工具。
  3. Doctor 文化——stale 注入清扫、codex trust 警告、junction 探测自愈：对标项目里没有等价物。
  4. 删除的勇气——Timeline、Web Agent、退役引擎都有完整的清理路径（包括 collector 清除名单）。

12.4 明显缺失

① git worktree 隔离（Claude Squad 的核心价值）——batch-run 跨项目并行已是强项，但同一项目的并行实例会互相踩工作区。② shell 补全。③ 终端侧的并行会话总览（目前只在 web 里）。

最终判断

CodeAgent 已经是同类定位里完成度最高的 "AI Engineering Shell"。它的护城河恰恰是那些别人没有的脏活：跨引擎会话转换、MCP 同步、doctor。它当前唯一的危险不是功能太少，而是三个"再堆一个功能就失控"的节点：引擎注册散落、gateway 悬空、危险默认值。

按 Phase 0→2 处理完，扩展性评分会从 6 回到 8+——而且全程不需要重写任何东西。
